# Firestore composite index — decision_memory (case_id, seq) — 2026-08-17

## Root cause, found deploying Cards 0–3

Deploying Cards 0/2/3 to `project-895d4ca8-d301-447d-916` (see
`evidence/deploy/deploy-20260817T022816Z.log`) surfaced a real runtime
error on `POST /api/instrument/earn`: HTTP 500,
`google.api_core.exceptions.FailedPrecondition: 400 The query requires
an index`, on the `decision_memory` collection group, for the exact
query `tower/memory.py:get_case_chain` runs
(`.where("case_id", "==", case_id).order_by("seq")`).

`infra/indexes.json` predates `tower/memory.py`'s Memory Bank — it was
last deployed 2026-08-15, before Cards 0/2/3 existed — so this specific
index was simply never defined. Confirmed via Cloud Run logs:

```
$ gcloud logging read 'resource.type="cloud_run_revision" AND resource.labels.service_name="unwind" AND severity>=ERROR' \
    --project project-895d4ca8-d301-447d-916 --limit 60 --freshness=10m
...
google.api_core.exceptions.FailedPrecondition: 400 The query requires an index.
You can create it here: https://console.firebase.google.com/v1/r/project/project-895d4ca8-d301-447d-916/firestore/indexes?create_composite=...
```

## Fix applied

Firebase CLI (`firebase --version` 15.27.0) is installed but not
authenticated against this project in this environment
(`firebase projects:list` → "No projects found") — a different
credential path than the `gcloud` ADC token already verified working for
the Cloud Run deploy itself. Applied the equivalent index directly via
`gcloud`, and added the same definition to `infra/indexes.json` (the
source of truth for the next `firebase deploy --only firestore:indexes`,
whenever Firebase CLI auth is set up in whatever environment runs it):

```
$ gcloud firestore indexes composite create \
    --project project-895d4ca8-d301-447d-916 \
    --collection-group=decision_memory \
    --field-config=field-path=case_id,order=ascending \
    --field-config=field-path=seq,order=ascending
Create request issued
```

Build took under 3 minutes (collection was near-empty). Verified READY:

```
$ gcloud firestore indexes composite list --project project-895d4ca8-d301-447d-916 --format=json
...
{
  "name": "projects/project-895d4ca8-d301-447d-916/databases/(default)/collectionGroups/decision_memory/indexes/CICAgJjFvYoK",
  "queryScope": "COLLECTION",
  "state": "READY",
  "fields": [
    {"fieldPath": "case_id", "order": "ASCENDING"},
    {"fieldPath": "seq", "order": "ASCENDING"},
    {"fieldPath": "__name__", "order": "ASCENDING"}
  ]
}
```

## Re-verified after the index went READY

```
$ curl -s -X POST https://unwind-hgeodtazqq-uc.a.run.app/api/instrument/earn
{"before_bp":0,"after_bp":500,"reason_code":"ALLOWED","allowed":true, ...}
```

`extractor_rookie` minted its first LOW-risk balance live, against real
Firestore, on the deployed service — 0bp → 500bp, `ALLOWED`. A second
call (idempotent by design — `instrument_earn` only mints when the
balance reads zero) correctly returned `before_bp == after_bp == 400`
(500 minted, 100 already spent by the first call's own gateway
re-check), still `ALLOWED`.

## What this was NOT

Not a code defect in `tower/memory.py` or `warrant/ledger.py` — the
query itself is correct and has always needed this index; the Firestore
emulator (used for all local/CI testing) does not enforce index
requirements the way production Firestore does, so no test in this
repository's suite could have caught this locally. It is a genuine
deployment/configuration gap, now closed and recorded in
`infra/indexes.json` so a future redeploy from a fresh project starts
correct.
